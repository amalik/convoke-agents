## Story

As a Convoke maintainer,
I want `agent-manifest.csv` regenerated by a command I run on purpose,
so that running the test suite never rewrites a tracked file behind my back — while a dev
tree keeps its ability to regenerate that file after the agent registry changes.

## ⚠️ The plan is the operator's recorded decision — read this before changing it

T54 records, 2026-08-24: *"extract generation into a deliberate path (`npm run generate:manifest`)
with `refreshInstallation` as a second caller, **then guard the refresh-side writes** — one copy,
two callers, same shape that worked for `downgrade-guard.sh`."* That is the plan. It is not open.

**An earlier version of this file forbade it** ("Do NOT wrap the write in `!isSameRoot`") and then
offered the operator a two-option choice that omitted their own decision. The prohibition was
correct for a guard *alone* — guarding without a regeneration path leaves a dev tree unable to
rebuild the manifest, so an agent added to `agent-registry.js` goes silently missing. It is **false
for guard-plus-command**, which is what T54 specifies: the command supplies the regeneration the
guard removes. Corrected 2026-08-25 by pre-implementation review.

**The one trap that is real.** `scripts/audit/install-scope-check.js` inspects only the files in its
`TRACKED` array (`:69`) and has **no assertion for write ops in an untracked file** — verified
2026-08-25. Extraction therefore does two things, and the second is easy to miss: it drops
`refresh-installation.js` from 11 write ops to 10, failing the snapshot; and it puts the write
somewhere the scope-safety net does not look at all. Fixing only the first re-greens CI while
silently shrinking the net. Both halves are in scope (AC6).

## Acceptance Criteria

**AC1 — A deliberate path exists, proven by an executable check — not by prose.**
Manifest regeneration is reachable through an explicit CLI entry at `scripts/` root (not
`scripts/lib/`; `no-process-cwd-in-libs` reserves `findProjectRoot()` for entry points, and the
existing entries — `convoke-doctor.js`, `convoke-check.js` — live there).

Verification is a **committed script** — `scripts/ci/verify-manifest-path.sh` or a test — that:

1. perturbs the tracked manifest (append a sentinel row, or truncate it);
2. runs the entry;
3. asserts `git diff --exit-code _bmad/_config/agent-manifest.csv` is clean;
4. restores the file on any exit path.

It must be demonstrated red before green: with step 1 removed it is a tautology; with step 1 present,
a wrong root, a no-op, or a deleted `package.json` script all leave the sentinel and fail.

> **Why a script and not a described manual run.** `code-review-convergence` `project-context.md:167`:
> *"Restructure, do not patch, when a round is correcting the previous round… Two failed attempts at
> the same fix predict a third."* This is the third attempt. Round 1 killed an md5-based AC4 that
> passed on the defective code; Round 2 replaced it with `npm run generate:manifest` + `git
> diff --exit-code` — **the same tautology, relocated**. Measured 2026-08-25: pointing the generator
> at a wrong root wrote 13,391 bytes there and left `git diff --exit-code` at **exit 0**. The named
> falsification turned the check *green*. A prose clause describing a manual run cannot be run red;
> a script can.

**AC1b — The package-repo contributor note.** After Task 4, a contributor adding an agent in this
repo must run the command. Add that where contributors read it. **Do not rewrite
`docs/agents.md:366`'s sentence** — it sits in "Journey 6: Extending the Framework", addressed to a
*consumer*, for whom `isSameRoot` is false, the refresh-side write still fires, and "no additional
wiring needed" stays true. Scope the note to the package repo. `scripts/README.md:15,33` are **not**
valid targets: they document `install-emma.js` and `install-wade.js`, both of which no longer exist —
a pre-existing staleness, filed separately, not this story's to fix.

**AC2 — One implementation, two callers.** The generation logic exists once, in `scripts/lib/`. The
CLI entry and `refreshInstallation` both call it. No behaviour is duplicated — the shape
`scripts/ci/downgrade-guard.sh` already uses.

**AC3 — The target-tree model is preserved.** Generation stays a function of the *target tree's*
state, not the registry alone. Four dependencies, all of which must survive extraction — (1) schema detection from the existing header (`isV610`, `refresh-installation.js:684`), (2) non-bme row
preservation (`preservedRows`, `:687`), and (3) Vortex and (4) Gyre exclusion filters
(`vortexExcluded` / `gyreExcluded`, read from the target tree at `:47-50`, applied at `:774-775`).
The exclusions are the easy one to drop: both repo configs are `excluded_agents: []`, so a
byte-identity check run in the package repo **cannot detect their loss**. Task 6 covers them with a
non-empty fixture.

**AC4 — The refresh-side write no longer fires.** `refreshInstallation(PACKAGE_ROOT, …)` performs
**no write** to `manifestPath` — asserted on the write op itself, not on file content. **Prefer
spying/counting the call over comparing mtime:** `node --test` runs files in parallel, so while any
`PACKAGE_ROOT` write survives elsewhere a concurrent suite can move the mtime and false-red this.

> **This AC is a deliberate, narrow exception to `test-fixture-isolation`.** That rule says "never
> against `PACKAGE_ROOT`" with "Exception. None." — and it binds tests that *write* or that assert on
> live repo state. AC4 asserts that **nothing is written**, which is the one shape the rule exists to
> protect. Six precedent sites already call `refreshInstallation(PACKAGE_ROOT, …)`:
> `tests/unit/refresh-installation-enhance.test.js:76,232,302,359` and
> `tests/unit/refresh-installation-artifacts.test.js:74,178`. Said explicitly so a reviewer applying
> the rule literally does not block AC4's own test.

> **Why not md5.** An earlier version of this AC compared the file's md5 before and after. Measured
> 2026-08-25: running `tests/unit/refresh-installation-enhance.test.js` on the **defective** code
> leaves md5 at `626d11e0…` while mtime moves `1787689180 → 1787689499`. The write fires and the
> assertion cannot see it, because the repo's manifest is already in sync with the registry. That AC
> passed on the code it was meant to condemn. See `verification-must-be-falsifiable`
> (`project-context.md:483`, "Exception. None.").

**AC5 — The extracted module is registry-driven against an arbitrary target.** (Retitled by Round 3: the demonstration uses a temp `projectRoot`, which is `isSameRoot === false` — a consumer-shaped tree. The dev-tree case is carried by AC1's executable check.) Injecting a new agent
into the registry and running the extracted module against a **temp `projectRoot`** updates the
manifest there. This is the constraint that makes a bare guard wrong, and it is demonstrated on the
module, not the CLI.

> **Execution-context rule for AC1, AC4 and AC5.** The package-repo guard lives on the **CLI entry
> only**; the extracted module takes `projectRoot` and an injectable registry (`no-process-cwd-in-libs`,
> `project-context.md:92`). Without that split these ACs have no legal home: AC7 confines the command
> to the package repo, while `test-fixture-isolation` (`:9`, "Exception. None.") forbids tests writing
> there — so the demonstrations would be required in the one tree they are banned from. That
> contradiction is what returned the 2026-08-24 draft; it recurred in a different pairing and was
> caught 2026-08-25.

**AC6 — The scope-safety net still covers the write.** The new module is added to
`install-scope-check.js`'s `TRACKED` with `expected: 1`; `refresh-installation.js` drops to `10`.
Arithmetic verified: exactly one `WRITE_OP_RE` match lives in the block (`fs.ensureDir`,
`fs.existsSync`, `fs.readFile` do not match, `:115`). The checker passes and its coverage of the
manifest write is preserved, not dropped. Both changed entries carry a comment saying why.

**AC7 — The entry refuses to run from inside an installed package.** The threat is real: `files`
includes `"scripts/"`, so the entry ships (verified: 457 files in the tarball). But **the guard the
previous version specified does not fire.** `findProjectRoot()` (`scripts/update/lib/utils.js:126-134`)
walks up from `process.cwd()` looking for a `_bmad` directory — and the tarball ships **355 `_bmad`
entries**. A consumer with cwd inside `node_modules/convoke-agents/` therefore gets
`projectRoot === packageRoot`, the contains-check passes, and the command runs. The refusal only
fired from outside the package directory, which is not where the risk is.

Discriminate on **development checkout**, not package root. `tests/` ships **zero** entries (verified
in the same pack listing), so its presence is a clean marker. Falsification: run the entry with cwd
inside a packed install → must exit non-zero. Same executable check as AC1, same script.
Do **not** add a `bin` entry.

**AC8 — The publish path is not broken.** `install-scope-check` runs inside `agent-surface-parity`
(`ci.yml:155`), which is in `publish.needs` (`ci.yml:452`). Editing the checker's snapshot is
explicitly permitted — the 2026-08-24 draft's AC7 forbade it, which is what made that story
unimplementable. **Do not wire regeneration into `prepack` or `prepare`:** `ci.yml`'s `fresh-install`
header records that it runs without `npm ci` and that adding either script breaks it, and
`fresh-install` is also in `publish.needs`. CI green before `done`.

**AC9 — Every AC *that is verified by a check* is shown able to fail.** (AC1b is a prose edit and AC8 is a CI outcome; neither has a mutation, and Round 3 caught the previous wording demanding one.) For each, the Dev Agent Record names the mutation
that turns it red — remove the guard, drop the exclusion filter, skip the `TRACKED` update. An AC
whose failure mode was never observed is not evidence (`verification-must-be-falsifiable`).

### §2 — What the previous draft got wrong

Recorded so the same conclusions are not re-derived. Full detail in **T54**.

1. **"Two writes"** → one. The taxonomy half is withdrawn.
2. **"`refreshInstallation` is the only generator"** → false for both files. `bootstrapTaxonomy`
   (`scripts/migrate-artifacts.js:149`) ships as the `convoke-migrate-artifacts` bin, so a deliberate
   taxonomy path already exists. The manifest is also written by `migrations/1.0.x-to-1.3.0.js` and
   `backup-manager.js`'s restore. The accurate claim: refresh is the only *from-registry* generator.
3. **"Regenerates from `agent-registry.js`"** → it merges registry rows into the existing file. AC3
   exists because of this.
4. **Old AC7 forbade touching the checker** → made the story unimplementable. AC8 now permits it.

### §3 — Rules that bind this story

- `test-fixture-isolation` — no test writes to the real tree. Pointed here because the defect *is* an
  unguarded write to the real tree.
- `path-safety-for-destructive-ops` — AC7's refusal path.
- `no-process-cwd-in-libs` — the new module takes `projectRoot`; only the CLI entry resolves it.
- `code-review-convergence` — R1 fires at commit prep; the reviewed set must equal the committed set.
- `verification-must-be-falsifiable` (`project-context.md:483`) — AC9 exists for this. The previous
  AC4 violated it outright.
- `backlog-write-discipline` — Task 9's T54 close is a move, not a status edit.
- `derive-counts-from-source` — the checker's expected counts are hand-maintained by design
  (a snapshot); do not "fix" them into a computed value, that would defeat the gate.

### §4 — Out of scope

- The taxonomy write (withdrawn, see §2.1).
- A *deliberate* CI gate on manifest-vs-registry drift — genuinely deferred, and the guard
  strengthens the case for it. **Corrected twice; do not re-derive either wrong version.** The first
  draft claimed neutrality. The second claimed `tests/unit/team-factory-wiring.test.js:45` and
  `tests/lib/portability-export-all.test.js:41` would go **red** after Task 4. Both wrong, measured
  2026-08-25: the committed manifest already equals generator output (md5 `626d11e0…` unchanged
  across a live `refreshInstallation(PACKAGE_ROOT)`), so guarding freezes *matching* bytes and both
  suites stay green — 12/12 and 5/5. Worse, `portability-export-all` cannot see registry drift at
  all: it consumes the `displayName` column, and **0 of 12 bme rows carry one** — all 41 rows with a
  displayName are non-bme, i.e. `preservedRows`. The direction is inverted: *today* the unguarded
  mid-suite write is what can turn `team-factory-wiring` red, and the guard removes that hazard along
  with the read-while-another-suite-writes race. Net effect is that registry drift becomes
  **invisible** to these two — which is an argument for the deferred gate, not evidence this story
  is non-neutral.
- `bootstrapTaxonomy` consolidation.
- **Two ACs from the superseded draft, dropped deliberately and recorded here rather than vanishing:**
  its containment clause ("no other `isSameRoot` branch changed" — this set has no blast-radius AC),
  and its re-survey of three benign-today writes (`agents/*.customize.yaml`, the gitignored
  `SKILL.md` wrappers, the `.claude/commands/bmad-agent-bme-*` delete). Both are reasonable follow-ups;
  neither is required for the defect this story fixes.

### ✅ Previously-open decision — resolved 2026-08-25

An earlier version asked the operator to choose between *unconditional* and *conditional*
regeneration in `refreshInstallation`. Both the framing and the options were wrong. Unconditional
cannot satisfy AC4 — `refreshInstallation(PACKAGE_ROOT)` is called at six live sites
(`tests/unit/refresh-installation-enhance.test.js:76,232,302,359`,
`tests/unit/refresh-installation-artifacts.test.js:74,178`) and would keep writing. And the option
the operator had **already chosen** in T54 — guard the refresh-side write, regenerate via the
deliberate command — was absent, because this file forbade it. Nothing is open; Task 4 implements
T54's decision.
